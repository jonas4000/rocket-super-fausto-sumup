## What this is

Firmware for a pay-per-dose coffee grinder. A customer picks a dose on the touchscreen, pays with a card on a SumUp Solo reader, and the device runs the grinder motor for the paid dose.

## Hardware

- **Board:** Waveshare ESP32-S3-Touch-LCD-2.8 (ESP32-S3, 16 MB flash, 8 MB octal PSRAM).
- **Display / touch:** 2.8" 240×320 IPS panel, ST7789 (SPI) with capacitive touch (I2C on SDA 1 / SCL 3). The touch chip depends on the board revision: V1 has a CST328 (0x1A, 16-bit registers), V2 (shipped since June 2026, our board) a CST3530 (0x58, 32-bit registers); `Display.cpp` detects which one at boot. Pins and protocols come from Waveshare's V1 and V2 demos (`ESP32-S3-Touch-LCD-2.8-Demo.zip` / `-V2-Demo.zip` on the wiki); all pin definitions live in `include/pins.h`. **The UI is landscape (320×240):** the panel is portrait natively; `lv_display_set_rotation` (`kRotation` in `Display.cpp`, 90°, use 270° if it's upside down) sets the ST7789 MADCTL, and LVGL rotates the touch points to match.
- **Grinder:** switched by GPIO15 (free header pin, not a strapping pin; needs an external pull-down) driving a solid-state relay (or relay module) rated for motor inrush current. Grinding is time-based per dose.
- **Payment terminal:** SumUp Solo, paired to the merchant account and reachable via the SumUp Cloud API.

## Stack

- PlatformIO with the Arduino framework (ESP32 Arduino core).
- LVGL for the UI.
- Wi-Fi + HTTPS (`WiFiClientSecure` / `HTTPClient`) for SumUp.

## Commands

PlatformIO is installed via `uv tool install platformio` (`~/.local/bin/pio`).

```sh
pio run -e esp32s3                     # build firmware (default env)
pio run -e esp32s3 -t upload -t monitor  # flash and watch serial
pio test -e native                     # host unit tests for lib/core
pio test -e native -f test_controller  # run a single test folder under test/
pio run -e sim && .pio/build/sim/program # terminal simulator (type 'help')
pio run -e ui-sim && .pio/build/ui-sim/program  # display simulator (SDL2 window)
pio run -e ui-snap                              # headless UI snapshots, see below
pio run -e sumup-cli && .pio/build/sumup-cli/program readers  # real SumUp API from the Mac
```

`sumup-cli` runs the firmware's `SumUpPayment` over libcurl with the keys from `include/secrets.h`: `me`, `readers`, `pay CENTS [refund]` (real checkout on the Solo, same 2 s polling / 60 s timeout as the controller), `status CLIENT_TRANSACTION_ID`, `terminate`. `pay` charges a real card, so use small amounts and `refund`.

The display simulator needs `brew install sdl2`. Its window shows the 320×240 device screen on the left (mouse = touch) and a fake SumUp reader with Approve/Decline, a motor LED and a Wi-Fi switch on the right (off = offline; with `--sumup`, SumUp and Supabase calls then fail like on the ESP32 without Wi-Fi). The PIN is in the window title. It persists settings/counters in `.pio/ui-sim-settings.txt` and the Flappy Beans top 5 in `.pio/ui-sim-flappy.txt` (delete to reset). The simulators' settings PIN is `1234` (`kSettingsPin` in ui-sim, hard-coded in ui-snap); the device takes `SETTINGS_PIN` from `include/secrets.h` (fallback `1234` without one). `.pio/build/ui-sim/program --sumup` sends real checkouts to the Solo from `include/secrets.h` instead (real money, title and panel say so; the panel shows the latest SumUp log line, the terminal all of them). In that mode, sales are also inserted into Supabase like on the device (`curlRequest`, retried every 10 s); with fake payments they are only printed. It runs `SumUpPayment` over the shared libcurl transport `src/host/CurlHttp.h` (also used by `sumup-cli`) in a detached thread. Closing the window mid-payment leaves the checkout on the Solo; clear it with `sumup-cli terminate`.

LVGL is configured entirely via `-D` flags in the shared `[lvgl]` section of `platformio.ini` (`LV_CONF_SKIP`), with no `lv_conf.h`; enable extra fonts/widgets there. The `esp32s3` env adds `LV_USE_STDLIB_MALLOC=LV_STDLIB_CLIB` (malloc, so large blocks land in PSRAM) and `LV_USE_ST7789`, and doesn't use `tools/cxx17.py` (the ESP32 core needs its own newer C++ standard).

**Checking UI layouts without a screen:** `ui-snap` runs the real UI on an in-memory display with a fake clock and scripted taps, writing BMPs (convert with `sips -s format png x.bmp --out x.png`, then view). `dump` prints the object tree with coordinates, which is the quickest way to debug overlapping widgets:
`.pio/build/ui-snap/program shot screensaver tap 20 120 shot idle tap 85 140 shot paying approve wait 2500 shot grinding dump` (the UI boots into the screensaver, so the first tap wakes it).
Steps: `tap X Y`, `press X Y`/`release` (hold), `state`, `offline`/`online`, `wait MS`, `approve`, `decline`, `shot NAME`, `dump` (also prints span-group text), `shots N`, `hour H`, `day D`, `score NAME N` (adds a Flappy Beans score; a top 5 score of 10+ also grants the free shot, so wait 61 s for it to expire), `easy` (Flappy Beans with wide openings, so steady taps score: `easy wait 10500 tap 236 205` then repeated `tap 160 120 wait 345`). Building `esp32s3` with a temporary `include/secrets.h` changes the project checksum, and PlatformIO then wipes all build folders, so rebuild the host envs afterwards. Run it from a scratch directory, since BMPs land in the cwd.

The simulator reads commands from stdin, so it can be scripted:
`printf "select 2\napprove\nwait 10\nq\n" | .pio/build/sim/program`

- `src/host/` — header-only host helpers shared by Mac envs (`CurlHttp.h`), on the include path via `-Isrc/host`.
- `supabase/schema.sql` — `coffee_log` sales table and RLS policy.
- `tools/`, `assets/` — fonts and Flappy Beans sprites (`assets/flappy/`) plus their converters.
- `src/ui/` — LVGL screens (`Ui`), shared by the firmware and the UI envs. The game screens are in `UiFlappy.cpp`.
- `src/ui-sim/` — SDL2 desktop display simulator (`ui-sim` env).
- `src/ui-snap/` — headless snapshot tool (`ui-snap` env).
- `src/sim/` — terminal simulator with fake reader/motor and a simulated clock (`sim` env only).
- `test/` — Unity tests run on the host (`native` env).
- `hardware/stl/` — 3D-printed parts (display mount, cover, cross struts); mounting hardware is listed in `README.md`.
- `README.md`, `LICENSE` — public description and MIT licence (third-party assets excepted).
- `include/pins.h` — GPIO assignments (display, touch, relay on GPIO15; `kRelayPin = -1` disables the relay output).

## Architecture

The core is a single state machine; UI, payment and motor control only talk to each other through it:

`Idle → AwaitingPayment → Grinding → Done → Idle`, with `PaymentFailed` / `Error` going back to `Idle`. From `PaymentFailed`, `retry()` sends a new checkout for the same dose and `cancel()` returns to `Idle`. Without a tap, it returns to `Idle` after `failedDisplayMs` (20 s), or after `timedOutDisplayMs` (5 s) when the failure was the 1-minute payment timeout (nobody at the machine).

Tapping a dose opens the `Portafilter` page (UI mode, controller stays `Idle`): a portafilter icon drawn from rectangles (`portafilterIcon` in `Ui.cpp`, one or two spouts matching `Dose::cups`) and "Is the portafilter inserted?", naming the right one (`Dose::portafilter`, single- or double-spout) and that grinding starts right after payment (or right away for a free shot). "Yes" calls `selectDose`, which sends the checkout to the reader; the grinder starts as soon as the payment succeeds. "Back" returns to the dose screen. The "Waiting for payment" screen has no portafilter note any more.

- **Offline:** `Connectivity` port (`Ports.h`); without one the controller counts as online. While offline, `selectDose` is ignored and `retry` returns to Idle, so no payment starts that couldn't be followed up. On the device, `WifiConnectivity` (`main.cpp`, SumUp builds only) is offline until the first connection and after 5 s without Wi-Fi (short reconnects don't count). The Idle screen then shows "Offline" with an amber crossed-out Wi-Fi badge, greyed-out non-tappable doses and "No connection · please try again later"; online there is no Wi-Fi indicator. `Ui::update()` rebuilds Main when `online()` changes.
- **Grinder only starts from a confirmed successful payment.** Never on a timeout, an ambiguous API response, or a lost Wi-Fi connection. Two deliberate exceptions, both inside `Controller`: the operator's hold-to-run Manual button, and a Flappy Beans free shot (granted only by `Controller::submitScore` for a top 5 score with at least 10 points, one shot, expires after `Config::freeShotMs`).
- **Motor safety is non-negotiable:**
  - The relay GPIO is driven OFF as the very first thing in `setup()`.
  - There is a hard maximum run time, independent of the dose timer.
  - A task watchdog cuts the motor if the firmware hangs.
- `Controller` never reads a clock itself: callers pass `nowMs` (`millis()` on device, a fake clock in sim/tests). Use unsigned subtraction for elapsed time so `millis()` wraparound is safe. `Controller::enter()` is the single place the motor is switched; any state other than `Grinding` forces it off.
- Keep pure logic (state transitions, pricing, dose timing) free of Arduino/hardware calls so it can be unit-tested with `pio test -e native`.
- Network calls must not block the LVGL loop: run them in a separate FreeRTOS task, or make them non-blocking.
- **Milestone shots** (total paid shots across all doses = 25, 50, 100, 200, 500, 1000; `Controller::isMilestone`) are free. Right after the payment succeeds, the controller calls `PaymentProvider::refundLastPayment()` and logs the sale with `refunded = true`, and `Controller::milestone()` holds the shot number for the UI (confetti + "You pulled shot #N. …" on the grinding screen). Grinding is never delayed for this. `SumUpPayment` remembers the transaction ID from the successful poll and queues `POST /v1.0/merchants/{mc}/payments/{transaction_id}/refunds` (full refund, no body fields). In the simulators, `shots N` sets the Single counter (e.g. `shots 24` makes the next shot #25); in ui-snap, `hour H` / `day D` set the local time.
- Price, grind time and sold count per dose live in the `Dose` array; `Controller::begin()` loads them via `SettingsStore` and clamps them to `Config` limits. Settings changes go through `Controller::setPriceCents/setGrindMs` (Idle only, clamped, saved immediately); the count increments and is saved when a payment succeeds.

### UI

- On top of the controller state, `Ui` has its own modes: `Main`, `Portafilter` (dose tapped, `pendingDose_`), `Screensaver`, `Pin`, `Settings`, plus the info pages `Info`, `HowTo`, `Stats` (no PIN). They are reachable only while the controller is `Idle`; any other state forces `Main`. Info and Settings use `buildHeaderClose()` (title + round ✕ top right). The dose screen (`buildIdle`, title "Pick your shot", kept short so it fits) has a round < top left that goes back to the screensaver (`parentOf(Main)`); it is hidden while a free shot is pending and when the game is switched off. Sub-pages (How to use, Stats) use `buildHeaderBack()` (round < top left). The PIN screen uses the same header as Settings (✕ top right). All of them go to `parentOf(mode)`, i.e. one level up.
- Custom fonts: the built-in Montserrat fonts have no bold, "€" or "·", and only LVGL's fixed icon set (the `LV_SYMBOL_*` glyphs are available only in the built-in fonts). Generated: `font_bold_{16,20,24,40}`, `font_pixel_{8,16}` (Press Start 2P, uppercase ASCII), `font_text_14` (Medium + €/·), and `font_icons_{14,20}` (Font Awesome: coffee, info, chart, stopwatch; the font files still contain unused users/GitHub glyphs); generated fonts have no space glyph unless their range includes it. `tools/gen_fonts.sh` uses `lv_font_conv` (via npx) to generate `src/ui/fonts/*.c` from `assets/fonts/` (Montserrat Bold under OFL, plus Font Awesome for icons). Always pass `--no-compress`: LVGL 9 has compressed fonts disabled and would draw boxes. To use a new glyph, add it to the script's `--symbols`/`--range` and regenerate.
- Grinding screen title: a random entry from `kGrindMessages`, picked once per grind and kept until it ends (never the same as the previous grind), followed by three animated dots (spans; hidden dots are transparent, not removed, so line breaks stay stable). Milestone shots show their own message instead.
- Screensaver: the round info and settings buttons top right (as on the dose screen) and two pixel-art arcade buttons at the bottom, "€ PAY FOR IT" (blue, wakes to the dose screen) and "PLAY FOR IT" with a bean icon (orange, opens Flappy Beans). Each is a light face (`kStartFace`) on a darker base of the same size, `kStartDepth` lower. Pressing animates the face down onto the base (`Ui::animateStart`). A tap finishes the press, springs back with overshoot, and the animation's completed callback wakes the screen (a tap anywhere else wakes it immediately). The labels use `font_pixel_8`, the € `font_pixel_16` (Press Start 2P, OFL, 1 bpp at its 8 px grid so the pixels stay crisp).
- **Flappy Beans** ("PLAY FOR IT", the orange arcade button next to PAY FOR IT on the screensaver; both come from `Ui::arcadeButton`). Modes `Game`, `GameName`, `Leaderboard`. Physics in `lib/core/FlappyGame` (unit-tested, field 320x216 above a 24 px ground, `FlappyConfig` holds the tuning); `Ui::updateGame()` steps it with the clock each frame and only moves/hides sprites. `Game` is built once and its phases (Get ready, playing, game over, pause) show/hide overlays, so taps in callbacks never rebuild. The bean flaps on `LV_EVENT_PRESSED` on the field; sprite buttons are clickable images on top. While playing: score top centre, "BEST" (leaderboard #1, or the current score once higher) top left, pause top right. "Get ready" has PAY INSTEAD (to the dose screen) / ▶ / leaderboard in one row; pausing shows PAY INSTEAD too. Game over: panel with score, best and medal (silver ≥ 10, gold ≥ 20), then PAY INSTEAD / TRY AGAIN / leaderboard. A top 5 score instead shows its rank for 1.5 s and then forces the name entry (`GameName`, own keyboard, no skip; starts empty for every player; OK needs a name; if the screensaver takes over, the score is saved with what was typed, "BEAN" if nothing). Then the top 5 page highlights the new row.
  - **Free shot:** a top 5 score with at least `Config::freeShotMinScore` (10) points earns one (`Controller::earnsFreeShot`; the minimum stops a board with free places, e.g. after a reset, from giving coffee away for 1 point). Lower top 5 scores are still listed. "Get ready" states the rule on a tag under the title ("TOP 5 WITH 10+ POINTS = FREE SHOT!"). Game over shows confetti and "NEW RECORD - FREE SHOT!" (above the old #1) or "TOP 5 #N - FREE SHOT!" for 3 s before the name entry; a top 5 score without a free shot shows "TOP 5 - RANK #N" for 1.5 s. Saving the name grants the shot. After the top 5 page's OK, Main shows "Free shot!", "Free" instead of the prices and a countdown (`Config::freeShotMs`, 60 s). While a free shot is pending, `Ui::update()` keeps the screensaver and the game away (forces Main, except on the Portafilter page), so it can't pass to the next person. `selectDose` then grinds without a checkout, even offline, and the shot isn't counted (no dose count or milestone) but is sent to the sales log as `refunded`, like a milestone; `Controller::freeGrind()` marks it for the grinding screen. "Reset to defaults" also clears the top 5 and any pending free shot.
  - **Game switch:** Settings has a "Flappy Beans" switch in the header (left of the ✕; the page has no room below). `Controller::setGameEnabled()` (Idle only) saves it via `SettingsStore::loadGameEnabled/saveGameEnabled` (NVS key `game`, ui-sim `.pio/ui-sim-game.txt`) and drops a pending free shot when switched off. Off means no screensaver either (it only leads to the game): `Ui::update()` forces `Main` out of every `isGameMode` mode, and inactivity returns to `Main` instead of the screensaver. "Reset to defaults" turns it back on.
  - `Leaderboard` (`Ports.h` → `SettingsStore::loadLeaderboard/saveLeaderboard`): 5 entries of name (A-Z, 0-9, spaces, max 10 chars, via `cleanName`), score, date (yyyymmdd, 0 = clock unknown, shown as "-"). 0 points never rank; ties rank below the older entry. `Controller::submitScore` stamps the date and saves. NVS: one blob under key `flappy2` (bump the suffix if the struct changes); `sanitize()` repairs whatever was loaded.
  - Sprites: "Flappy Beans" by 1UP.capsule (OpenGameArt, CC BY 4.0): keep the credit in `assets/flappy/LICENSE.txt`, the README and the generated file's header. `tools/flappy_to_lvgl.py` converts `assets/flappy/*.png` into `src/ui/flappy_img.c` (ARGB8888, bean rotatable; background and ground RGB565; about 600 KB of flash). It crops and scales some sprites for landscape (see `SPRITES` in the script). Rerun it after changing a sprite: `uv run --with pillow python3 tools/flappy_to_lvgl.py`. Labels without a sprite (PAY INSTEAD, TRY AGAIN) use `textButton`: brown pixel text on a blank copy of the play button sprite (`fb_button_text` 96 px / `fb_button_text_wide` 120 px, made by the script), so they match the ▶ and podium buttons in a row. `font_pixel_8`/`font_pixel_16` cover space to `_` (uppercase ASCII).
- Wall clock: `WallClock` port (`Ports.h`) gives the local date (yyyymmdd) and hour, or returns false before NTP sync. It's used by `Controller` (daily shot count, reset when the date changes) and for the Flappy Beans dates. `Stats` (`Ports.h`: today's day + count, best day, date of the last "Reset to defaults", games played, free shots used, total grind ms) is persisted via `SettingsStore::loadStats/saveStats` (NVS keys `day`, `dayShots`, `bestDay`, `lastReset`, `games`, `freeShots`, `grindMs`). Grind time is added in `Controller::enter()` whenever a grinding state is left. "Reset to defaults" zeroes the dose counts and all stats except `lastReset` (it always saves the stats, also while the clock is unknown). On the device: `NtpClock` with `configTzTime` and `TIME_ZONE` from `secrets.h` (UTC without it). ui-sim: the Mac's clock. ui-snap: `hour H` / `day D` (the hour defaults to -1 = unknown).
- Info has two pages: How to use and Stats (no PIN). Stats is a list: shots today, total per dose, most on a single day, total grind time (seconds the motor ran, Manual runs included), Flappy Beans games (rounds finished), free shots used, "Settings last reset" (dd.mm.yyyy, or "Never"; not updated while the clock is unknown). It is longer than the screen and scrolls below the fixed header.
- Randomness: `Ui::nextRand()` steps a state, stirs in the clock and mixes with MurmurHash3 `fmix32`. Don't go back to a plain LCG plus clock: the clock then only touches the low bits, and the first message after boot was always the same. Seed with real entropy via `Ui::seedRandom()` (`esp_random()` on the ESP32, `std::random_device` in ui-sim); ui-snap stays unseeded for repeatable runs.
- **Never rebuild screens inside an LVGL event callback** (it deletes the object being clicked). Callbacks only set `mode_` or call the controller, and `Ui::update()` rebuilds when `(mode_, state)` changes.
- Screensaver: shown at boot, and after 10 s of no touch (30 s on the Info pages, `Ui::isInfoPage`, for reading, and on the Flappy Beans name entry, `GameName`; each key press restarts it) (`lv_display_get_inactive_time`) while Idle, including from PIN/settings. Controller state changes count as activity. A tap on the root wakes it, so layout containers (`box`, `spacer`) are made non-clickable and taps fall through.
- Settings sit behind a 4-digit PIN (`SETTINGS_PIN` in `secrets.h`). They hold +/- steppers for price (€0.05) and grind time (0.05 s, shown as e.g. "2.60 s") per dose. Prices start at €1.00 (`Config::minPriceCents`, SumUp's minimum card payment); pressing − at the minimum shows "SumUp minimum per payment: €1.00" for 3 s (`priceNote_`, floating over the bottom row, not clickable, hidden again in `update()`). The counters are on Info > Stats, not here. Below the dose cards (compacted so everything fits; the list would scroll under the fixed header with more doses) is "Reset to defaults", which opens the `ResetConfirm` page (same layout as the payment-problem screen, Cancel / Reset). `Controller::resetSettings()` restores the price and grind time that each dose had at construction, turns the game back on and zeroes the dose counts and every stat except "Settings last reset" (so milestones start over at #25). Right of it, "Manual" is a hold-to-run test button: `LV_EVENT_PRESSED` calls `Controller::startManualGrind()` (state `ManualGrinding`, Idle only, unpaid and not counted), release or press-lost calls `stopManualGrind()`, and `Ui::update()` also stops it whenever the button isn't in `LV_STATE_PRESSED` or the page changed. `tick()` caps it at `maxRunMs`. Settings is not rebuilt on state changes (only `Main` is), so the held button survives.
- Look follows the owner's mockups: near-black background (`kBg`), dark grey bordered cards (`kCard`/`kBorder`), white text, grey secondary text, brand blue `#00A2CD` (`kFg`) for accents, progress and the primary button, amber for problems. Helpers in `Ui.cpp`: `card`/`tapCard`, `makeButton` styles (`Primary`, `Neutral`, `Round`, `Tile`, `Ghost`), `plain`/`box` (non-clickable containers).
- LVGL flex gotcha: a content-sized column with `LV_FLEX_ALIGN_SPACE_BETWEEN` overlaps its children. Use `START` for content-sized columns.

## SumUp integration

The device talks to the SumUp Cloud API directly; there is no backend. This was a deliberate choice (the device is in a trusted location).

- The Solo is paired to the merchant account for the Cloud API (on the Solo: Connections > API > Connect, then `POST /v0.1/merchants/{mc}/readers` with the pairing code, or via the dashboard). `sumup-cli readers` must list it as `paired`.
- `SumUpPayment` (`lib/sumup`) implements the flow. Its `PaymentProvider` methods never touch the network; they record what is wanted and return the cached status. A FreeRTOS task (`startSumUpTask`) calls `work()`, which makes at most one blocking request per call. State is behind a `std::mutex`.
  1. Checkout: `POST /v0.1/merchants/{mc}/readers/{reader_id}/checkout` with `total_amount` (cents, `minor_unit` 2), `description` (dose name) and the required `affiliate` object (`app_id`, `key`, a unique `foreign_transaction_id` = `grinder-<boot random>-<counter>`). The response's `data.client_transaction_id` identifies the payment. 4xx means Failed. No answer (network error/5xx) means Failed plus a terminate, since it may have reached the reader.
  2. Each controller poll (2 s) triggers `GET /v2.1/merchants/{mc}/transactions?client_transaction_id=...`. 404 means the transaction doesn't exist yet (keep waiting). Only the top-level `status == "SUCCESSFUL"` gives `Succeeded`; `FAILED`/`CANCELLED`/`REFUNDED` give `Failed`; anything else stays pending until the controller's 60 s timeout. Nested `events[].status` is ignored (parsed with an ArduinoJson filter).
  3. Cancel/timeout: `POST .../readers/{reader_id}/terminate`, then the abandoned transaction is re-checked every 5 s (6 answered checks, about 30 s online), and refunded if it was paid anyway (the customer got no coffee). Requests without a usable answer (offline, timeout, 408/429/5xx) don't use up the terminate tries or the checks: the terminate is retried every 2 s (blocking other jobs) and the checks continue until the connection is back. So a card tapped on the Solo (own connection) while the grinder was offline is refunded once it reconnects, unless it reboots meanwhile.
  - Every start/cancel bumps a generation counter. Responses for an older generation never change the current status, so a late "SUCCESSFUL" can't start the grinder for a different checkout. A terminate is always sent before a queued new checkout.
  - The device has no public endpoint, so webhooks (`return_url`) are not used.
- Amounts are integers in minor units (cents) plus a currency code. Never use floats for money.
- **Credentials** (Wi-Fi, SumUp, Supabase, the settings PIN, the time zone) live in a gitignored `include/secrets.h`, and a committed `include/secrets.example.h` documents the expected defines. Never commit real values. Without `secrets.h` the firmware still builds (via `__has_include`), with Wi-Fi and Supabase disabled and the serial fake payment (`a`/`d` keys) instead of SumUp. `-DFAKE_PAYMENT` forces the fake even with secrets.

## Supabase sales log

- After each successful payment, `Controller` calls `SalesLog::recordSale()` exactly once (milestones with `refunded = true`). A Flappy Beans free shot is logged too, also as refunded, when it starts grinding. On the device, `src/firmware/SupabaseLog` formats the row with `formatSaleJson` (`lib/core/SaleJson`, unit-tested) and queues it. The row is only `{"dose":"Single","price_cents":50,"refunded":false}`; the timestamp is Supabase's `created_at` default, so a retried sale gets its arrival time, not its payment time.
- A FreeRTOS task POSTs to `{SUPABASE_URL}/rest/v1/coffee_log` and retries every 10 s on network errors, 408, 429 or 5xx. Other 4xx responses are dropped so they can't block the queue. The queue lives in RAM, and the NVS counters remain the source of truth.
- The table and its insert-only RLS policy are in `supabase/schema.sql`. Its optional, commented-out `alter database ... set timezone` shows `created_at` in local time; the device's own zone is `TIME_ZONE` in `secrets.h` (via `configTzTime`).
- Auth: the `apikey` header is always sent. `Authorization: Bearer` is added only for legacy JWT anon keys, never for `sb_publishable_...` keys.
- TLS currently uses `setInsecure()` (TODO: pin roots like `SumUpCa.h`). SumUp itself verifies the certificate against the pinned ISRG Root X1/X2 (`api.sumup.com` is served by Let's Encrypt); if SumUp changes CA, payments fail safe until `SumUpCa.h` is updated.
- The simulators print the JSON row; only `ui-sim --sumup` (real payments) also sends it.
- `SUPABASE_URL` is the bare project URL (`https://<project>.supabase.co`); the code appends `/rest/v1/coffee_log`.
